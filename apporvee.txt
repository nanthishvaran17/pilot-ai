# MASTER BUILD PROMPT: AI-POWERED SMART PROJECT REQUIREMENTS & PLANNING PLATFORM

## 1. ROLE AND OBJECTIVE

Act as a world-class product architect, senior full-stack engineer, UX researcher, UI/UX designer, AI workflow engineer, database architect, security engineer, and QA automation specialist.

Design and implement a production-oriented, premium web application that collects project requirements through a highly intelligent, dynamic, personalized form experience.

The application must not look or behave like a traditional Google Form, generic survey, or boring multi-page questionnaire.

Build a polished, responsive, intelligent requirements-gathering platform that adapts to each user's answers, asks only relevant questions, remembers progress, prevents unnecessary repetition, and generates a complete, structured project specification from the user's responses.

Working product name: **ProjectPilot AI**.

The product name must be configurable.

Primary objective:
Help a user transform an initial idea into a clear, complete, actionable project blueprint through an easy, personalized, adaptive questionnaire.

The platform must be usable by non-technical users while collecting enough technical information for developers to implement the project correctly.

Do not merely create a landing page or static UI mockup. Implement the actual frontend, backend, database, form logic, validation, persistence, and project-report generation.

---

## 2. CORE PRODUCT PRINCIPLES

Follow these principles throughout the application:

1. Ask only questions that are relevant to the current user and their project.
2. Never force users to answer every question.
3. Use conditional logic to show or hide questions based on previous answers.
4. Distinguish essential requirements from optional preferences.
5. Allow users to skip, defer, or mark a requirement as undecided.
6. Ask for clarification only when an answer is ambiguous or insufficient for the next step.
7. Never repeatedly ask for information already provided.
8. Support users who have no technical knowledge.
9. Translate technical concepts into simple language with examples.
10. Provide advanced technical options only when relevant.
11. Save progress automatically and allow users to resume later.
12. Never invent requirements or silently convert assumptions into confirmed decisions.
13. Clearly label confirmed answers, inferred suggestions, unanswered questions, and unresolved decisions.
14. Let users review, edit, and approve all generated requirements.
15. Make the experience fast, accessible, mobile-friendly, and visually excellent.

The system must optimize for completion, clarity, low cognitive load, and accurate requirement collection—not for the number of questions asked.

## 4. USER JOURNEY

Implement the following end-to-end journey.

### Step 1: Welcome and project creation

Show a premium welcome screen with a concise explanation of the platform.

Primary action: "Start Planning".

Allow the user to:
- Create a new project.
- Resume an existing project.
- View saved drafts.
- Duplicate a previous project.
- Rename or archive a project.

Ask only the minimum information needed to begin:
- Project name or working title.
- What the user wants to accomplish.
- Intended audience or users, if known.

Allow the user to start with incomplete information.

### Step 2: Understand the initial idea

Provide a simple free-text field:

"Describe what you want to build."

Allow natural-language input in English or Tamil-English transliteration where practical.

Provide optional example prompts.

Use AI, when configured, to identify:
- Project objective.
- Target users.
- Main problem.
- Expected outcome.
- Possible modules.
- Known constraints.
- Missing critical information.

Do not force the user to manually repeat information already stated in the description.

Present the extracted summary for confirmation.

### Step 3: Build a personalized questionnaire

Generate a project-specific question plan using the initial description and confirmed answers.

Questions should be grouped into logical sections, such as:
- Project goals.
- Target users.
- Core features.
- User workflows.
- User interface.
- Automation.
- AI capabilities.
- Data and integrations.
- Roles and permissions.
- Security and privacy.
- Reports and exports.
- Deployment.
- Testing.
- Future expansion.

Only include relevant sections.

For example:
- If the user does not need AI, do not force an AI configuration section.
- If the project does not generate certificates, do not ask detailed certificate-design questions.
- If the user selects a web application, ask web-related questions.
- If the user also selects Android, ask mobile-specific questions.
- If the user has no technical knowledge, use guided defaults and simple explanations.

### Step 4: Adaptive questionnaire engine

Implement a real rules-based conditional questionnaire.

Each question must support:
- Unique identifier.
- Section identifier.
- Display label.
- Plain-language explanation.
- Input type.
- Required or optional status.
- Default value, where appropriate.
- Validation rules.
- Conditional visibility.
- Dependencies on previous answers.
- Skip eligibility.
- Help text.
- Option to mark "Not sure yet".
- Optional recommendation.
- Answer persistence.

Supported question types:
- Single-choice radio group.
- Multiple-choice checkboxes.
- Dropdown.
- Short text.
- Long text.
- Number.
- Date.
- File upload.
- Yes/no.
- Ranking.
- Conditional follow-up.
- Optional priority selection.

Do not display all questions simultaneously.

Ask a manageable number of questions per step. Prefer one focused question at a time when that improves clarity; use compact groups for closely related settings.

Provide:
- Back.
- Continue.
- Skip.
- Save and exit.
- Review answers.
- Resume later.

Do not make the user lose progress when navigating backward or changing an answer.

### Step 5: Contextual intelligence

Implement the following behaviors:

A. Relevant follow-ups:
Ask follow-up questions only when the preceding answer creates a meaningful need for clarification.

B. Smart defaults:
Offer sensible recommendations for common project types, while clearly identifying them as suggestions.

C. Duplicate prevention:
Do not ask the same question in different wording unless confirmation is genuinely necessary.

D. Contradiction detection:
Identify conflicting answers, explain the conflict in plain language, and let the user resolve it.

E. Missing requirement detection:
Identify important missing information before producing the final specification.

F. Confidence and uncertainty:
Distinguish user-confirmed requirements from AI-inferred possibilities.

G. Adaptive complexity:
Allow a beginner-friendly mode and an advanced technical mode.

H. Optional depth:
Provide "Basic", "More details", and "Advanced settings" where appropriate.

I. Change propagation:
If a user changes an earlier answer, recalculate dependent questions and derived requirements without deleting unrelated information.

J. Transparent assumptions:
List unresolved questions and assumptions rather than inventing answers.

AI must never autonomously finalize sensitive, financial, security, or externally consequential decisions without explicit user approval.

## 12. TECHNICAL IMPLEMENTATION

Use a maintainable, typed architecture.

Preferred stack:
- Frontend: React, TypeScript, Vite, Tailwind CSS.
- UI components: accessible reusable component library.
- Backend: Python FastAPI.
- Database: PostgreSQL.
- ORM and migrations: SQLAlchemy and Alembic.
- Authentication: secure session-based authentication or appropriately implemented JWT.
- AI integration: provider abstraction supporting configured local or hosted models.
- File processing: validated backend processing.
- Background jobs: task queue when required.
- Storage: private object storage or appropriately secured local development storage.
- Testing: frontend tests, backend unit tests, integration tests, and end-to-end tests.

If the existing repository already has a working stack, inspect it first and preserve compatible architecture instead of unnecessarily rewriting the application.

### Data model

Design appropriate entities for:
- Users.
- Organizations, if required.
- Projects.
- Project memberships.
- Templates.
- Template versions.
- Sections.
- Questions.
- Conditional rules.
- Responses.
- Requirements.
- Assumptions.
- Unresolved decisions.
- Uploaded files.
- Generated documents.
- Audit events.
- Export jobs.

Use proper foreign keys, indexes, uniqueness constraints, transactions, and tenant isolation where applicable.

Never store all project data in a single unstructured field if doing so would prevent reliable querying, validation, or versioning.

### API design

Implement documented APIs for:
- Authentication.
- Project CRUD.
- Template retrieval.
- Dynamic question retrieval.
- Answer saving.
- Conditional visibility evaluation.
- Requirements summary.
- Completeness analysis.
- Blueprint generation.
- File uploads.
- Export generation.
- Project history.
- Administration.

Use consistent response schemas, error handling, pagination where appropriate, and API documentation.

### AI reliability

- Validate structured AI outputs against schemas.
- Use deterministic rules for critical business logic.
- Treat uploaded documents as untrusted data.
- Prevent prompt injection from uploaded files from changing system instructions.
- Keep API keys on the server.
- Never expose credentials in frontend bundles or logs.
- Handle timeouts, rate limits, retries, and unavailable models.
- Provide a useful fallback when AI is unavailable.
- Require user confirmation before saving AI-generated decisions as confirmed requirements.

## 17. ACCEPTANCE CRITERIA

The product is ready for its first production-oriented release only when:

- A user can create and save a project.
- Questions adapt correctly to previous answers.
- Irrelevant questions remain hidden.
- Optional questions can be skipped.
- Users can resume drafts without losing responses.
- Changing answers updates dependent requirements.
- Confirmed answers and AI suggestions are distinguishable.
- A complete requirements summary can be reviewed and edited.
- The blueprint is generated from actual saved responses.
- DOCX, PDF, and other advertised exports work correctly.
- Permissions are enforced on the backend.
- The application works on desktop and mobile.
- Important failure states are handled.
- Automated tests cover core workflows.
- Deployment and configuration instructions are documented.
